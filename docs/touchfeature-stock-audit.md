# TouchFeature와 호환펜 — 2026-10-27

사용자는 정품 샤오미 펜과 정품 키보드를 보유하지 않으며 호환펜만 보유한다.
호환펜 모델, 블루투스 및 버튼 지원은 아직 확인하지 못했다. 정품 페어링·인증·OTA·
OOB 협상을 검증했다고 보고하거나, 호환펜에 동일한 기능이 있다고 가정하지 않는다.
NVTCapacitivePen 입력 장치가 존재한다는 사실도 실제 펜 연결의 증거가 아니다.

## 스톡 명령과 crDroid 제어의 차이

검사 대상은 Pad 5 OS1.0.6.0.TKXMIXM 덤프의 boot.img에서 추출한 ARM64 Image다.
스톡 커널은 Linux 4.14.180-perf-g98d7380da이다. Image의 kallsyms에서 121919개
심볼을 복원했고, 이름 스트림의 256개 단위 marker 전부를 대조했다.
아래 주소는 실행 중 커널 주소가 아닌 압축 해제한 Image의 파일 오프셋이다.
Image SHA256: `03cdc4da64895b55f6f165052b9f57bf978e48805657bd7518af5a078df220de`.

- `nvt_set_cur_value`: 0xa41298. mode 20 분기는 0xa41324부터다.
  값의 하위 nibble은 펜 식별/세대 값이며, 0x10 이상은 연결, 미만은 해제다.
  연결 수와 선택된 식별 값을 갱신하고 work를 예약한다. 단순 boolean이 아니다.
- `disable_pen_input_device`: 0xa418a8. 0xa419a4부터 확인되는 실제 SPI 쓰기는
  `EVENT_MAP_HOST_CMD`, `0x7b`, disable 값이다. 이 명령은 입력 활성화 제어이며
  mode 22의 ID·주파수·전압 전달 명령이라는 근거는 없다.
- `nvt_get_mode_value`: 인접한 0xa41238 함수는 mode가 20보다 크면 실패한다.
  `nvt_set_cur_value`의 다른 모드는 일반 배열 경로로 진입한다. 따라서 단순히
  mode 22를 전달해 성공값을 얻는 것으로 스톡에서 OOB가 동작한다고 판단할 수 없다.

현재 crDroid nt36523 소스는 mode 20 값을 `!!value`로 바꾸어
`pen_input_dev_enable`에 저장한다. 예를 들어 스톡 해제 값 0x01/0x02를 이 경로로
보내면 입력을 오히려 활성화한다. `/sys/touchpanel/pen`도 boolean 선택값이지
스톡 연결 프로토콜을 구현한 인터페이스가 아니다.

따라서 작성 중이던 mode 20 → boolean sysfs HAL 초안은 빌드 입력에서 철회했다.
기존 IInputControl의 명시적 펜 활성화·세대 선택은 유지한다. 스톡 ioctl HAL의
기본 제외도 유지하며, TouchFeature/OOB 연결이 완료되었다고 표시하지 않는다.
이 조사로 실제 커널을 변경하거나 호환펜에 정품 연결 이벤트를 합성하지 않았다.

## mode 22에서 아직 필요한 근거

원본 BluetoothExtension의 MiuiBleOobHelperService는 첫 번째 ID를
`(id << 8) | 1`, 두 번째 ID를 `(id << 8) | 3`으로 전달한다. TX 주파수 변경은
0x31, 전압 변경은 0x32를 전달한다. 이것은 앱 측 요청 형식의 확인이다.
터치 컨트롤러가 받는 SPI 명령 형식이 확인된 것은 아니다.

사용자 공간 인터페이스 자체는 추가할 수 있다. 하지만 이를 완성하려면 실제 지원
펌웨어의 명령과 응답/실패·suspend 시 처리 방식을 확인하고, 그 위에 한정된 커널
속성과 HAL을 만들어야 한다. 값만 저장하는 속성이나 0x7b·공장 검사 명령으로의
대체는 OOB 구현으로 취급하지 않는다. 정품 펜이 없으므로 실기기 OOB 검증도 남는다.

호환펜에서는 우선 필기 입력, 실제 지원되는 버튼, 켜기/끄기와 설정 복원을 검증한다.
IDT 값은 태블릿 충전 회로에서 읽은 값으로 취급하고, 검증되지 않은 호환펜 자체의
배터리 잔량·연결 상태로 표시하지 않는다.
